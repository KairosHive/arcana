## Detail

### `arcana/arcana.py:88` — Relative media paths are resolved against <install>/../images, a directory that cannot exist or be created in a packaged app
**Severity:** high  ·  **Dimension:** —

arcana.py:88 sets `IMAGES_ROOT = os.path.abspath(os.path.join(APP_ROOT, '..', 'images'))` — i.e. the repo-root `images/` folder one level above the package. `resolve_path` (:292-294) returns `p if os.path.isabs(p) else os.path.join(IMAGES_ROOT, p)`, and every media reader goes through it: make_thumbnail_bytes (:139), make_resized_bytes (:165), read_audio_mono (:186), encode_image (:337), encode_thumbnail (:353), make_melspec_png (:2412), the /audio route (:634), the colour-transfer callback (:2189-2190) and save_images (:3120, :3164). db.py:71 duplicates the same constant and never uses it. In a package, `APP_ROOT/..` is the install directory; `images/` will not be there, and nothing can create it. The symlink present in this checkout (`images -> /c/Users/skite/.../images`) is a developer-machine artefact that will not survive packaging.

**Failure scenario.** A dataset built on another machine (or migrated via arcana/legacy.py, which records POSIX-relative paths — bundle.py:105) yields relative paths. On the packaged app every one of them resolves to `C:\Program Files\Arcana\images\<rel>`, which does not exist: cv2.imread returns None, /thumb returns 404 for every tile, and the grid renders as an empty grey wall with `[ERROR] Could not load image:` lines going to a console nobody sees.

**Suggested fix.** Make the media root a per-dataset property stored alongside the dataset (or a user-chosen folder in Settings) rather than a constant derived from __file__, and surface a clear 'media folder not found — locate it' prompt in the UI when resolve_path misses. Delete the dead duplicate at db.py:71.

### `arcana/arcana.py:134` — _win_longpath corrupts UNC paths into an OS-rejected form
**Severity:** high  ·  **Dimension:** —

`_win_longpath` (arcana.py:134-140) prepends the extended-length prefix `\\?\` to `os.path.abspath(p)` whenever it isn't already present. That prefix is only valid for drive-letter paths; a UNC path must be written `\\?\UNC\server\share\...`, with the leading `\\` replaced. I verified on this machine: `_win_longpath(r"\\nas\photos\arcana\output\stories\s\poetry_injected\x.png")` returns `\\?\\\nas\photos\...`, and opening it raises `OSError: [Errno 22] Invalid argument` — the OS rejects the path form itself, so it is not a missing-file error you can catch and ignore. It is used at line 2321 on a path under STORIES_DIR, i.e. under APP_ROOT.

**Failure scenario.** The app is installed on, or the user's Documents folder is redirected to, a network share (`\\fileserver\home\antoine\Arcana`) — standard in schools and studios. The user clicks "Inject poetry", the diffusion pipeline runs for minutes, and `out_img.save(save_path)` at line 2322 throws OSError 22. The callback has no try/except, so Dash surfaces a raw traceback and all the generated images are lost.

**Suggested fix.** Only apply the prefix to drive-letter paths, and use the UNC form otherwise: if `ap.startswith('\\\\')`, return `'\\\\?\\UNC' + ap[1:]`, else `'\\\\?\\' + ap`. Also gate the whole helper on the path actually exceeding MAX_PATH, since most consumers of these paths (cv2, described below) cannot handle the prefix at all.

### `arcana/arcana.py:143` — Four unbounded-by-bytes lru_caches on media encoders never release memory
**Severity:** high  ·  **Dimension:** —

`make_thumbnail_bytes` maxsize=50000 (143), `make_resized_bytes` maxsize=2000 (164), `thumb_b64_for` maxsize=50000 (179) and `make_waveform_png` maxsize=20000 (213) are all keyed on the path string and cap *entry count*, not bytes. A 192px JPEG is ~8 KB, a 900px preview ~120 KB, a 900x160 waveform PNG ~20-40 KB. Fully populated these hold roughly 400 MB + 240 MB + 800 MB of encoded media that is never evicted for the process lifetime, on top of the module-level CLIP-ViT-H-14 (line 391, ~2 GB fp16), the lazily-loaded CLAP, VGG19 and the ModFlows encoder — all in one process, with no `cache_clear()` anywhere.

**Failure scenario.** A user browses a 13k-image dataset for an hour, panning the scatter and hovering points. The Flask process climbs past 3-4 GB of resident media caches plus ~3 GB of models. On a 8 GB laptop the OS starts swapping or the process is killed; the packaged app window simply disappears with no error.

**Suggested fix.** Replace the entry-count caches with a byte-budgeted cache (track `len(data)` and evict oldest until under a fixed budget, e.g. 256 MB total), or drop the in-process caches entirely and rely on the `Cache-Control: public, max-age=31536000` headers already set on /thumb, /preview and /awave.

### `arcana/arcana.py:493` — Base stylesheet is fetched from codepen.io at every page load, so the offline desktop app renders unstyled
**Severity:** high  ·  **Dimension:** —

`external_stylesheets=["https://codepen.io/chriddyp/pen/bWLwgP.css"]` is the only remote asset in the whole app (verified: it is the sole http(s) URL in arcana.py, db.py, palette.py, style.py and lab_transfer.py). It supplies the grid/typography base that arcana/assets/custom.css only overrides on top of. Dash serves its own component bundles locally by default, so this single CDN link is the entire difference between an offline-capable UI and a broken one.

**Failure scenario.** Packaged app launched with no internet (or on a corporate network that blocks codepen.io): the browser cannot fetch the stylesheet, the page renders with default browser styling — unreadable dark-on-default text, collapsed columns — and there is no error message explaining why.

**Suggested fix.** Download bWLwgP.css into arcana/assets/ (Dash auto-serves everything in the assets folder alphabetically, so name it e.g. 00-base.css so it loads before custom.css) and delete the external_stylesheets argument.

### `arcana/arcana.py:642` — /audio reads the whole media file into RAM per request and serves no Range requests
**Severity:** high  ·  **Dimension:** —

Lines 641-643 do `with open(full,'rb') as f: data = f.read()` and return the entire file in one Response. There is no `Accept-Ranges`/206 support, so the browser's <audio> element cannot seek without re-fetching, and Werkzeug serves requests on threads so several full copies can be live at once. The page can mount many players simultaneously (an <audio> per carousel group at 2765 and per story scene at 2626).

**Failure scenario.** User previews a 45-minute uncompressed WAV (48 kHz stereo 16-bit ~ 500 MB). One request allocates a 500 MB bytes object; dragging the scrub bar three times issues three more full 500 MB reads because there is no Range support, and the browser buffers the whole file before playback starts.

**Suggested fix.** Replace the manual read with `flask.send_file(full, mimetype=mime, conditional=True)`, which streams the file and handles Range/206 and If-Modified-Since. Derive the mimetype with `mimetypes.guess_type` rather than the two-branch guess at 639-640 (.ogg and .flac are currently mislabelled audio/wav).

### `arcana/arcana.py:1735` — Moodboard and selection saves collapse same-named files from different folders
**Severity:** high  ·  **Dimension:** —

`save_moodboard_images` builds the destination as `os.path.join(output_dir, os.path.basename(path))` (line 1735) and `save_moodboard_selected_results` does the same (line 1792), then `shutil.copy2` on top. Neither disambiguates the source directory. The third save path, `save_images` at line 3121-3124, gets this right: `prefix = hashlib.md5(path.encode("utf-8")).hexdigest()[:8]; safe_name = f"{prefix}_{basename}"`. The two moodboard callbacks then report `f"Saved {saved} images"` using the number of copy attempts, not the number of distinct files on disk.

**Failure scenario.** A user moodboards 30 shots from `2023\IMG_0042.jpg`, `2024\IMG_0042.jpg`, ... (camera basenames repeat across every import folder). The UI reports "Saved 30 images to ...\moodboards\final" and the folder contains 6 files; the other 24 were overwritten. The user has no way to know which survived.

**Suggested fix.** Use the same path-hash prefix as line 3123 in both places, or reconstruct the source subtree under output_dir, or append a counter on collision. At minimum, count only copies whose destination did not already exist and report the real number.

### `arcana/arcana.py:1790` — Moodboard "Save Selected Images" silently drops every grouped (twin) result
**Severity:** high  ·  **Dimension:** —

`save_moodboard_selected_results` filters with `if path and os.path.exists(path) and not path.startswith("group::")` and never resolves group ids. But `moodboard_similarity_search` creates `daq.BooleanSwitch(id={"type": "select-image", "index": f"group::{g['gid']}"})` (line 2054) for every group with more than one image whenever "Group twins" is on (which is the default, line 1067). The prompt-mode saver handles this correctly via `_current_path_for_gid` (3092-3097, used at 3111); the moodboard saver has no equivalent.

**Failure scenario.** User runs a palette search with grouping on, clicks "Select All", then "Save Selected Images". 40 cards are selected but only the 12 single-image ones are written. The confirmation says "Saved 12 images" (or "No images selected" if every result grouped), with no indication that 28 selections were discarded. The user believes they exported their whole selection.

**Suggested fix.** Reuse the `_current_path_for_gid` logic: pass `grouped-results` and `carousel-state` in as State and resolve `group::<gid>` ids to the currently displayed path before copying, exactly as `save_images` does at 3106-3113.

### `arcana/arcana.py:2371` — _write_cached_spec writes the shared PNG non-atomically; concurrent writers corrupt the file on disk
**Severity:** high  ·  **Dimension:** —

`_write_cached_spec` (2371-2377) opens the destination `cache_specs/<key>.png` directly with mode "wb" and writes. The key is a hash of path+mtime+params (2379), so two callers rendering the same clip target the exact same file. Concurrency is guaranteed here: `update_images` submits up to 64 prewarm jobs to `SPEC_EXEC` at line 2813 while the browser is simultaneously fetching `/aspec` for the same paths, and the negative-caching bug at 2362 means neither side ever short-circuits on an existing file.

**Failure scenario.** Prewarm thread and the /aspec request thread both finish computing the same spectrogram. Both truncate and write the same PNG; the interleaved bytes leave a truncated or mixed file. The current process never notices (it recomputes anyway), but on the next app launch `_read_cached_spec` returns those bytes and the browser renders a broken or half-grey spectrogram for that clip, permanently, because the mtime-based key still matches.

**Suggested fix.** Write to a unique temp file in the same directory (`tempfile.mkstemp(dir=SPEC_CACHE_DIR)`) and `os.replace()` it onto the final name, which is atomic on both NTFS and POSIX.

### `arcana/arcana.py:2499` — Main callback loads the latent pickle with no error handling; any bad/missing file kills the whole UI silently
**Severity:** high  ·  **Dimension:** —

`df = load_data(latent_name, n_dim=dim, modality=modality)` is called bare. `load_data` (369-371) does `pd.read_pickle(latent_path)` with no existence check and no try/except, and this is the callback that drives image-display, scatter-plot, story-cache and all three group stores. Any of: the file deleted while the app is open, a build interrupted mid-`to_pickle` (db.py:1213) leaving a truncated file, a pickle written by an incompatible pandas/numpy, or a stale dropdown option after the user removed a dataset — raises out of the callback. `load_index` (382-386) is equally unguarded and is called at 2553 and 2650.

**Failure scenario.** A build is interrupted with Ctrl-C partway through `df.to_pickle(...)`. The dataset still appears in the dropdown because both `latent_space_*.pkl` and `index_*.pkl` exist and the dropdown matches on filenames only (get_matching_datasets, 307-326). Selecting it raises `EOFError: Ran out of input`. With debug=False nothing is drawn and nothing is said — the user sees a blank plot area and assumes the app is broken.

**Suggested fix.** Wrap the load in try/except inside `update_images` and return `[html.Div('Could not open dataset <name>: the data file is missing or damaged. Rebuild it.')]` plus an empty figure. Have `load_data`/`load_index` check `os.path.exists` first and raise a typed `DatasetError` the callback can render. Write dataset files atomically in db.py (temp file + `os.replace`) so an interrupted build never leaves a half-written pickle that the dropdown advertises.

### `arcana/arcana.py:2499` — Every scatter click rebuilds and re-transmits the entire 82k-point figure (8.85 MB of JSON)
**Severity:** high  ·  **Dimension:** —

`update_images` takes `scatter-plot.clickData` and `mode-select.value` as Inputs and `scatter-plot.figure` as an Output, and unconditionally re-reads the latent pickle at 2499 and rebuilds the full figure at 2504-2545 before it even looks at what triggered it. Every point carries its absolute path as customdata (line 2506). Measured on latent_space_2022-onward_image_2d.pkl (82,173 rows, 10 label traces, 6.9 MB of path strings): px.scatter build 0.82 s, plotly to_json 0.28 s, payload 8.85 MB — per fire. `uirevision` at 2545 preserves the camera but does not prevent the retransmission or the browser-side re-render of all 82k WebGL points.

**Failure scenario.** User clicks one dot to preview an image. Dash re-reads the 8.9 MB pickle, rebuilds ten traces, serialises 82k absolute paths and pushes 8.85 MB over the websocket; the browser re-uploads the whole point cloud to the GPU. Each click costs ~1.5 s and ~9 MB, and rapid clicking queues them.

**Suggested fix.** Split the figure build into its own callback keyed only on `dataset-dropdown.value`, and have the click/search paths return `dash.no_update` for the figure (or use Patch/`extendData` to update only the highlight trace). Drop `custom_data=['path']` in favour of a compact row index and look the path up server-side.

### `arcana/arcana.py:2571` — Story mode raises IndexError when a search result path is not in the latent DataFrame
**Severity:** high  ·  **Dimension:** —

Line 2568 does `row = df[df["path"] == s["path"]]` and 2571/2573 immediately index `row["x"].values[0]` with no emptiness check. The path comes from `search()` (line 411), which reads it out of `idx2path` in the *index* pickle, while `df` comes from the *latent* pickle. `get_matching_datasets` (307-326) pairs those two files by name and modality only — nothing verifies they were built from the same run. db.py's `--reuse_index` flag (1084) explicitly allows rebuilding one without the other.

**Failure scenario.** User rebuilds `index_myphotos_image.pkl` after moving their photo folder, but the old `latent_space_myphotos_image_2d.pkl` is still on disk. Story mode finds a match in the new index whose absolute path does not exist in the old DataFrame, and `row["x"].values[0]` raises `IndexError: index 0 is out of bounds for axis 0 with size 0`. With debug=False the "Generate Story" button silently does nothing every time it is pressed.

**Suggested fix.** Skip (and count) story chunks whose path is missing: `if row.empty: continue`, and report "3 of 8 scenes could not be placed — this dataset's index and layout were built at different times. Rebuild it." Better: stamp a build id/UUID into both the index pickle and the latent pickle in db.py and refuse to pair mismatched files in `get_matching_datasets`.

### `arcana/arcana.py:2571` — Story mode crashes with IndexError when the index and latent file disagree about a path
**Severity:** high  ·  **Dimension:** —

`row = df[df["path"] == s["path"]]` (arcana.py:2568) joins the search index to the latent DataFrame by exact string equality on an absolute path, then immediately does `row["x"].values[0]` (lines 2571 and 2573) with no emptiness check. The path on the left comes from `idx2path` inside index_<name>_<mod>.pkl; the path on the right comes from a completely separate latent_space_<name>_<mod>_<n>d.pkl. The two files carry no shared build id, timestamp, or item count, and get_matching_datasets (arcana.py:307-326) pairs them on filename alone, so a latent file left over from an earlier build is offered as a valid dataset.

**Failure scenario.** User builds `--name japan --n_components 2`, later adds photos and re-runs `--name japan --n_components 3`. The second run rewrites index_japan_image.pkl and writes latent_space_japan_image_3d.pkl but leaves the stale 2d file untouched (db.py:1137-1138, 1213). The dropdown still offers "japan - image (2D)". Story mode searches the NEW index, gets a path for a newly added photo, finds no matching row in the OLD DataFrame, and `row["x"].values[0]` raises `IndexError: index 0 is out of bounds for axis 0 with size 0` (verified). Uncaught callback -> Dash error overlay with a traceback.

**Suggested fix.** Guard the lookup (`if row.empty: continue` plus a visible "this scene has no position in the current layout" note), and stamp both artifacts with a shared build id + item count at write time in db.py so load_data/load_index can refuse a mismatched pair with a plain-language message rather than pairing them by filename.

### `arcana/arcana.py:2650` — The whole usearch index is re-read from disk and re-restored on every single search click
**Severity:** high  ·  **Dimension:** —

`load_index()` (382-386) does `pickle.load` of the index pickle then `Index.restore(blob)` and is called fresh inside the callbacks at 2553 (story), 2650 (prompt) and 1864 (moodboard). The restored Index is a callback local, so it is thrown away when the callback returns and rebuilt on the next click. Nothing caches it — unlike `_CLAP` (397-405) and color_transfer's `_encoder` (187-211), which do cache. Measured on the dataset present in this repo: arcana/databases/index_2022-onward_image.pkl is 188 MB on disk, the blob is 180.5 MB for 82,173 items, and both the blob and the restored index are live simultaneously during restore (~360 MB peak).

**Failure scenario.** User types three prompts in a row on the 82k-image dataset. Each Search re-reads 188 MB from disk and re-materialises a 180 MB index, ~540 MB of pointless I/O and three ~360 MB allocation spikes, with a multi-second freeze per click on a spinning disk.

**Suggested fix.** Add a module-level `_INDEX_CACHE: dict[(name, modality)] -> (Index, idx2path)` holding at most one or two entries, evicting the previous dataset when the dropdown changes. Same treatment for `load_data()` at 369-380, which is likewise re-read per callback (line 2499).

### `arcana/color_transfer.py:42` — ModFlows resolution assumes a source checkout: sibling directory, sys.path injection of a generic `src` package, and a git-lfs clone into the install dir
**Severity:** high  ·  **Dimension:** —

Line 42: `MODFLOWS_DIR = Path(__file__).parent.parent / "modflows"` — a sibling of the *package* directory, which is only true in a source checkout. In a wheel install that resolves to site-packages/modflows; under PyInstaller it resolves inside sys._MEIPASS. `_ensure_modflows_available()` (lines 136-147) then does `sys.path.insert(0, str(MODFLOWS_DIR))` and line 200 does `from src.encoder import Encoder` / line 237 `from src.inference import run_inference` — a top-level module named `src` reached only through a runtime sys.path mutation, which PyInstaller's static analysis cannot follow, so it will never be bundled. ### `arcana/arcana.py:143` — Media caches are keyed on the raw request path with no mtime, so edited files never refresh
**Severity:** low  ·  **Dimension:** —

`make_thumbnail_bytes` (line 143-144), `make_resized_bytes` (164-165), `thumb_b64_for` (179-180) and `make_waveform_png` (213-214) are `@lru_cache`d on the path string handed in by the request, before `resolve_path` normalises anything and with no mtime or size component. Contrast `_spec_cache_key` (line 2379-2381), which does include mtime. Two consequences: the same file reached as `C:/a/b.jpg` and `C:\a\b.jpg` occupies two entries (50000 + 2000 + 50000 + 20000 slots of decoded image bytes are reachable from client-controlled strings), and a file replaced on disk is served from the stale entry forever. Separately, `_write_cached_spec` (2371-2377) writes PNGs into SPEC_CACHE_DIR keyed on absolute path + mtime with no eviction, so renaming the dataset folder orphans the entire cache rather than reusing it.

**Failure scenario.** A user re-exports a photo over the same filename (a routine Lightroom/Photoshop round trip) and the app keeps showing the old version in the grid and the preview until they restart it — with no cache-clear control anywhere in the UI. Meanwhile cache_specs/ under the install directory grows without bound and is fully invalidated by moving the image folder.

**Suggested fix.** Include `os.path.getmtime(full)` and size in the cache key (as `_spec_cache_key` already does), and normalise the path with `os.path.normcase(os.path.normpath(...))` before it becomes a key. Give SPEC_CACHE_DIR a size cap with LRU eviction on disk, and key it on a content or (size, mtime) fingerprint rather than the absolute path so a moved folder reuses the cache.

### `arcana/arcana.py:151` — Thumbnail generation raises on images with an extreme aspect ratio
**Severity:** low  ·  **Dimension:** —

`make_thumbnail_bytes` computes `scale = max_side / max(h, w)` then `new_w, new_h = int(w * scale), int(h * scale)` and calls `cv2.resize(img, (new_w, new_h), ...)` (arcana.py:150-152). When the aspect ratio exceeds max_side (192 here, 128 in `encode_thumbnail` at arcana.py:357-359) the short side truncates to 0 and cv2.resize raises `!ssize.empty()`. Neither the function nor `thumb_endpoint` (arcana.py:501-509) has a try/except, so the exception escapes into Flask.

**Failure scenario.** A dataset contains a stitched panorama or a scanned strip, e.g. 4000x18 px. Hovering that point on the scatter plot requests /thumb, cv2.resize raises, and Flask returns a 500 with an OpenCV traceback in the console; the same file also breaks the moodboard gallery thumbnail. In a packaged app the traceback goes nowhere the user can see and the thumbnail is just permanently blank.

**Suggested fix.** Clamp both dimensions to at least 1: `new_w, new_h = max(1, int(w * scale)), max(1, int(h * scale))` in `make_thumbnail_bytes` (line 151) and `encode_thumbnail` (line 358), and wrap the body in try/except returning None so the endpoint answers 404 instead of 500.

### `arcana/arcana.py:1672` — Uploaded reference images accumulate forever, and there is no upload size limit
**Severity:** low  ·  **Dimension:** —

Lines 1658-1676 base64-decode the upload and write it to output/_external_refs/ext_<md5>.<ext> (1672). Nothing ever deletes these. No `MAX_CONTENT_LENGTH` is set on app.server, and dcc.Upload transports the file as a base64 data URI, so the callback holds the ~1.34x-inflated string (`upload_contents`) and the decoded bytes (`decoded`, 1660) simultaneously, on top of what Flask already buffered for the request body.

**Failure scenario.** User drops a 300 MB TIFF onto the similarity-search zone. The browser holds a ~400 MB base64 string, Flask buffers the request, and the callback holds both the 400 MB string and the 300 MB decoded bytes at once — roughly 1 GB of transient memory for one drag-and-drop. Over months of use, _external_refs/ silently fills the disk with every reference image ever tried.

**Suggested fix.** Set `app.server.config['MAX_CONTENT_LENGTH']` and reject oversized uploads with a clear message; write the decoded bytes in a streaming fashion and drop the base64 string first; put _external_refs under the user cache dir with an age- or size-based sweep at startup.

### `arcana/bundle.py:315` — Bundle.__init__ leaks the open ZipFile (and the Windows file lock) whenever validation fails
**Severity:** low  ·  **Dimension:** —

Line 315 assigns `self._zip = zipfile.ZipFile(path, 'r')` and the constructor then raises BundleError at 320 (no manifest), 324 (unknown format), 326-330 (future format version) and 335-338 (item count mismatch) without closing it.
